# Database schema

Reference for the v1 SQLite schema. Every table that ships in v1 is
created by `socialhome/migrations/0001_initial.sql` (1,717 lines).
This doc groups those tables by domain so a contributor can find what
they need without reading the SQL top-to-bottom.

The migration file is the **source of truth** for column types,
indexes, and foreign keys; this page exists to navigate it. When
anything below contradicts the file, the file wins.

## Conventions

- TEXT columns hold ISO-8601 UTC timestamps unless otherwise noted.
- `instance_id` and `user_id` are 32-character base32 strings derived
  from an Ed25519 public key (§4.1.2 / §4.1.3) and never reassigned.
- Foreign keys reference public ids (string keys), never integer
  surrogates, so federation events can carry the same key across
  instance boundaries.
- JSON columns are stored as TEXT and validated at the service layer.
- GPS coordinates are stored already-truncated to 4 decimal places
  (§4 / [`principles.md`](./principles.md)).
- Schema migrations after v1 follow the `0002_*.sql` pattern; the v1
  file collapses what the spec called "migrations 0001–0033".

## Identity, users, auth

| Table | Purpose |
|---|---|
| `instance_identity` | Single-row table (`id='self'`) with the HFS's long-term Ed25519 keypair, optional ML-DSA-65 PQ key, `home_lat` / `home_lon` (4dp-truncated, nullable — populated by the HA / HAOS adapter on startup from HA Core's `/api/config`; standalone mode leaves them NULL unless the operator configures a location), and routing secret. Migration `0034_instance_keywrap_key.sql` adds a long-lived X25519 **key-wrap** keypair (`keywrap_public_key` + KEK-wrapped `keywrap_private_key`, both NULL for pre-upgrade rows → lazily minted on next startup) — the static recipient key a seed-holder seals the space content key to when handing it to an unpaired subscriber (Phase 5b). Only the public half is published (at GFS registration); the private half never federates and is never logged. Migration `0035_instance_keywrap_sig.sql` adds `keywrap_sig TEXT` (NULL for pre-safeguard rows → lazily minted on next startup) — the Ed25519 self-signature `b64url(sign(identity_seed, keywrap_public_key))` binding the key-wrap pubkey to this household's identity. Published at GFS registration so a remote sealer can verify the GFS-served key-wrap key end-to-end (`derive_instance_id` + signature, `federation/keywrap_seal.verify_keywrap_binding`) and never trust a value a malicious GFS could substitute. |
| `instance_config` | Generic key/value store for instance-level settings the platform adapter or services need to persist. Federation-inbox base URL keys: `ha_federation_base` (pushed by the Home Assistant integration — Home Assistant's own URL, which the ha/haos adapters suffix with `/api/socialhome/inbox`, the HA-hosted view forwarding into the add-on) and `federation_base_url` (admin-set via `PUT /api/admin/federation/external-url` — the address Social Home is reachable at directly, suffixed with its own `/federation/inbox`). Held separately because the two mean different things; the admin-set value takes precedence when present. No migration — the table is schemaless. |
| `users` | Local household users — username, display name, profile picture hash, admin flag, theme, status, locale, child-protection fields, soft-delete state, `last_seen_at` (most recent WS disconnect — drives "Last seen X" rendering after a server restart, see `docs/protocol/presence.md` § Online status), `source` (`manual` vs `ha`), `external_id` (provider-side stable id scoped by `source` — the 32-hex HA `user_id` for `source='ha'`; lets the picture lifter / future presence bridge join via `person.attributes.user_id` without re-resolving the username, and keeps SH identity stable across HA display-name renames), and `tz` (the user's personal IANA timezone, auto-detected from the browser on first login via a `PATCH /api/me` probe; falls back to the household tz when still `'UTC'`). Migration `0040_user_identity_keys.sql` adds the per-user **identity** key family (independent user identity Phase 1): `user_identity_public_key` / `user_identity_private_key` (the user's own Ed25519 keypair — public half hex, private seed KEK-wrapped; NULL for pre-upgrade rows → lazily minted on next startup by `ensure_user_identities`, and minted at provision), plus `user_pq_algorithm` / `user_pq_public_key` / `user_pq_private_key` reserved for the Phase-2 PQ hybrid (NULL in Phase 1). Only public halves ever federate; behaviour-neutral — the legacy `user_id` stays canonical. Migration `0041_user_identity_anchor.sql` adds `identity_anchor` — the **immutable** `user_id` derivation input (`derive_user_id(instance_pk, identity_anchor)`): a uuid4 minted **once** at provision for v_26+ standalone users, and the **frozen username** for existing rows (backfilled in the migration) and haos users, so a user's `user_id` stays stable across a rename. Set once at provision and never mutated. Migration `0043_user_handle.sql` adds `handle` — the public, per-household-unique, case-insensitive `@handle` (UNIQUE index `idx_users_handle_nocase`; new users get `handle = username` at provision). Unsigned public **display metadata** (not part of the signed identity binding) that federates on `USER_UPDATED` / `USERS_SYNC` like display name + picture. Migration `0049_derived_admin_user_id.py` is a **repair**: the first admin of a standalone / ha household used to be minted with a synthetic `user_id` of the literal form `uid-<username>` instead of a derived one, so no peer could self-certify them (`derive_user_id(author_pk, anchor) == author_user_id` always failed) and every post they authored was dropped by the public-space relay. The migration re-derives the id from `instance_identity.identity_public_key` (username-anchored, matching the `0041` backfill and the haos owner), stamps `identity_anchor = username`, and rewrites the retired value in **every** column of every table that holds it — the ~20 `REFERENCES users(user_id)` children and the ~90 FK-free user-id columns (`space_posts.author`, `space_members.user_id`, `tasks.created_by`, …) alike, enumerated from the live schema so a future table can't be missed. `remote_users` is deliberately excluded (a `uid-admin` there is a *peer's* admin, not ours). No `instance_identity` row → clean no-op; a DB with only derived ids is untouched; re-runs are no-ops. |
| `user_profile_pictures` | WebP bytes for household-level profile pictures, keyed by `user_id`. Separate table so `SELECT * FROM users` stays cheap. |
| `remote_users` | Users on paired remote instances. Carries display name, alias, picture hash, public key, `deprovisioned_at`, and `synced_at`. Same `user_id` namespace as `users`. Migration `0040_user_identity_keys.sql` adds `user_identity_public_key` (hex Ed25519, NULL until set) and `user_pq_public_key` (reserved for PQ, NULL in Phase 1) — the remote user's own identity public key, stored only after the dual-signed binding on `USERS_SYNC` / `USER_UPDATED` verifies against the sender's pinned instance key (independent user identity Phase 1; see `docs/protocol/user-identity.md`). Migration `0041_user_identity_anchor.sql` adds `identity_anchor` (NULL until a verified v_26 binding carries it) — the immutable `user_id` derivation input, stored alongside the verified key. Migration `0043_user_handle.sql` adds `handle` — the remote-side cache of the peer's public `@handle`, mirrored from inbound `USER_UPDATED` / `USERS_SYNC` (unsigned display metadata). NULL for a peer at an older proto version that doesn't ship the field; the `upsert_remote` write uses `COALESCE(excluded.handle, handle)` so a non-handle profile edit never nulls a previously-cached handle. Migration `0044_remote_user_move_redirect.sql` adds the **move-out redirect** (MO-1) `moved_to_user_id` / `moved_to_instance_id` / `move_issued_at` / `move_link` — when a person moves out to a new household they get a NEW household-scoped `user_id` there, and this row (their OLD identity) gets a forwarding pointer to it. The pointer is set only after the inbound dual-consent `MoveLink` on `USER_MOVED` (or the `USER_IDENTITY_RESOLVE` pull backstop) verifies; `move_issued_at` (tz-aware ISO-8601, sorts lexically) is the **monotonic** replay guard — an incoming link `<=` the recorded value is dropped, so a replayed older link can't resurrect a stale identity. The signed link JSON is stored in `move_link` and re-served verbatim on a later resolve request. Old (un-moved) rows stay NULL = "not moved" and keep their `user_id` untouched — the `user_id` is provenance, never re-keyed. `resolve_current_identity` walks `moved_to_user_id` to the chain tip. See `docs/protocol/move-out.md` and `docs/protocol/capabilities.md` v_27. |
| `api_tokens` | Per-user API tokens (HA mode and integrations). Stores `token_hash` only — the plaintext is shown to the user once. |
| `platform_users` | Standalone-mode local accounts (`platform/standalone/`). Empty in HA mode. Stores password hash, email, notify endpoint. |
| `platform_tokens` | Bearer tokens for `platform_users`. Hash-only storage. |
| `password_reset_tokens` | Admin-issued, single-use, 1h-TTL tokens that let a user set a new password. Stores SHA-256 of the raw token; `used_at` flips on consume so a token can't be replayed. |
| `auth_audit_log` | Append-only trail of password-bearing auth events: `login_success`, `login_failure`, `reset_issue`, `reset_redeem_success`, `reset_redeem_failure`. Each row carries `username` (NULL when the request didn't carry a recoverable principal), `ip_address`, and free-form `metadata` JSON. Read by admins via `GET /api/admin/auth-audit`. Pruned after 90 days by `auth_audit_cleanup_scheduler` so a brute-forcer can't grow it without bound via repeated failed logins. |

## Federation: peers, pairing, outbox, replay

| Table | Purpose |
|---|---|
| `remote_instances` | One row per paired peer. Holds the peer's `instance_id`, identity public key, KEK-encrypted directional session keys, inbox URL, status (`pending_*` / `confirmed` / `unpairing` — `unpairing` is an **unpair tombstone**: a peer we unpaired while it was offline, kept only so the outbox can deliver our queued `UNPAIR` (30-day bound, tracked by that outbox row's `expires_at`); hidden from every ordinary read, refused by the §24.11 pipeline for everything but its own `UNPAIR`, its `remote_users` / `peer_user_visibility` rows dropped at tombstone time, and replaced by a new pairing with the same household — see `docs/protocol/pairing.md` § Unpairing), source (`manual` / `space_session` — `space_session` marks a **space-scoped** row created by the §D2b invite-link bootstrap redeem: CONFIRMED so the space can federate against it, but excluded from every social surface (DMs, `USERS_SYNC`, presence, friends, calendar/app peer pickers, moments, highlights, the public-space directory snapshot and the auto-pair vouching relay) via `federation_repo.list_social_instances`. Its `remote_inbox_url` is empty — no address is exchanged on that path; it is reached instead through the connection server that introduced the pair, using `remote_keywrap_pk` + `relay_via`, see below), `proto_version` (monotonic int the peer advertised via `INSTANCE_CAPABILITIES_UPDATED` at startup — drives sender-side gating; see `docs/protocol/capabilities.md`), and the negotiated `sig_suite` (`ed25519` / `ed25519+mldsa65`). `home_lat` / `home_lon` (4dp-truncated, nullable) hold the peer's household coordinates — populated from the `PAIRING_PEER_ACCEPT` body on first contact or updated by inbound `LOCAL_HOME_LOCATION_CHANGED` events (capability v5+); used by the Connections Map tab. The `local_alias` column (added in migration `0005`) holds the admin's local-only rename of the peer; `NULL` means "fall back to `display_name`". Never federated — purely local UX state surfaced in Friends / Connections / DM views. The `share_home` column (added in migration `0006`, `INTEGER NOT NULL DEFAULT 1`) is a per-pair flag controlling whether this household's home coordinates are shared with the peer: `1` (default) — coordinates are included in the outbound `LOCAL_HOME_LOCATION_CHANGED` fan-out; `0` — the peer is skipped during fan-out, and flipping to `0` immediately fires a null-coord revoke envelope. Never federated — local-only policy state. The `remote_keywrap_pk` column (added in migration `0052`, `TEXT` nullable) holds the peer's static X25519 **key-wrap** public key (hex), verified bound to `remote_identity_pk` at seat time via `keywrap_seal.verify_keywrap_binding`. Set only on `space_session` rows, where every outbound §24.11 envelope is sealed to it before the connection server carries it (`federation/gfs_relay_transport.py`); `NULL` on every ordinary peer, which has an address and needs no seal. It cannot be re-derived — `remote_identity_pk` is Ed25519 and the session keys are one-way HKDF outputs. The `relay_via` column holds the introducer's `instance_id` for an auto-paired peer and, on a `space_session` row, the **base URL of the connection server that introduced the pair** — the same question ("who do I go through to reach this peer"), and the two sources never mix on one row. The `capabilities_seen_at` column (added in migration `0023`, `TEXT` nullable, no default) is an ISO 8601 UTC timestamp of when the peer last advertised its capabilities (`INSTANCE_CAPABILITIES_UPDATED`); `NULL` means it has never advertised — paired but mid-first-handshake — so `proto_version` is the conservative default rather than a confirmed value. The inbound handler stamps it on every valid advertisement (even a same-version re-announce). Powers the admin federation-compatibility panel's `capabilities_known` flag. Local-only. |
| `pending_pairings` | In-flight QR pairings. Stores own DH keypair, peer DH/identity material once received, `verification_code` (SAS), inbox URL, status, and expiry. KEK-encrypted private DH until pairing confirms. |
| `pairing_relay` | Admin-pending `PAIRING_INTRO_RELAY` requests received from a paired peer (§11.9). |
| `federation_outbox` | Pending outbound envelopes — `event_type`, encrypted `payload_json`, `attempts`, `next_attempt_at`, `status`. `expires_at` is defaulted at enqueue from the §4.4.7 policy: `NULL` (retry forever) for security-critical / structural NEVER_DROP events, a 7-day TTL for ordinary ones. A successfully **delivered row is deleted** (`mark_delivered`), not tombstoned — the receiver's 2xx satisfies at-least-once and nothing reads delivered rows. The `OutboxProcessor` runs a periodic retention sweep that (a) marks pending rows past `expires_at` as `failed` (`expire_past_retention`; NEVER_DROP rows skipped) and (b) DELETEs terminal (`delivered`/`failed`) rows older than `TERMINAL_GRACE` (24 h) in bounded batches (`purge_terminal`). The table is therefore **bounded**: failures are retained 24 h for diagnostics then purged, and any pre-change `delivered`/`failed` backlog is reclaimed over successive ticks. (`delivered_at` is now vestigial — kept additively to avoid a column-drop migration.) A hard **per-peer pending cap** (`MAX_PENDING_PER_PEER`, default 1000) bounds the table per peer independently of the TTL: at/over the cap, `enqueue` evicts that peer's oldest *droppable* (non-NEVER_DROP) pending row (`evict_oldest_droppable`) before inserting the new one, so a permanently-offline peer plus a busy space can't flood the outbox. NEVER_DROP rows are never evicted — if the backlog is entirely NEVER_DROP the new row goes in over the cap rather than dropping a security/structural event. `enqueue` only inserts for a household we still hold (`INSERT … SELECT … WHERE EXISTS` on `remote_instances`, and for an `unpairing` tombstone only the `UNPAIR`): the check is serialized with the unpair purge on the single writer, so a send still in flight when the pairing ends cannot strand a row behind it. The retention sweep also deletes, whatever their status, rows whose `remote_instances` row is gone (`purge_orphaned`) — the backstop for a crash between a teardown's row delete and its outbox purge; an unpair tombstone keeps its row and so its queued `UNPAIR`. |
| `federation_replay_cache` | `msg_id` → `received_at` for inbound dedup. Pruned by `infrastructure/replay_cache_scheduler.py`. |
| `network_discovery` | Peer-graph cache for §11.10 BFS path-finding — one row per `(instance_id, discovered_via)` edge. Compound PK so multiple paths to a peer are independent rows. |
| `gfs_connections` | Paired Global Federation Servers — `gfs_instance_id`, public key, inbox URL, status. |
| `gfs_space_publications` | Which public spaces are currently published to which GFS connection. `status` mirrors the GFS-returned publication state (`active` \| `pending` \| `banned`, default `active`). |

## Household feed and content

| Table | Purpose |
|---|---|
| `preferences` | Polymorphic preferences table. `id='household'` holds the single household-wide row (feature toggles `feat_feed`, `feat_pages`, `feat_tasks`, `feat_stickies`, `feat_calendar`, `feat_bazaar`, `feat_presence`, `feat_gallery` — all defaulting to 1 — plus `household_name` and `tz`; `allow_link_preview`, default 1, is the admin switch for author-side link preview cards). A row with `id=<user_id>` holds per-user sidebar preferences (`hide_highlights`, `hide_momentum`, `hide_bazaar` — all defaulting to 0). The Python scope policy (`PREFERENCE_SCOPE` in `socialhome/domain/preferences.py`) is the authoritative list of which columns belong to which scope. The `tz` column on the household row is the IANA wall-clock anchor (`'UTC'` at install; mirrored from HA Core's `time_zone` on adapter startup in `ha` / `haos` mode; admin-editable in `standalone` mode). Calendar events created without an explicit `tz` resolve through this column at the floor of the fallback chain. |
| `feed_posts` | Household-level posts. Type enum covers `text`, `image`, `video`, `transcript`, `poll`, `schedule`, `file`, `bazaar`. Holds reactions JSON, comment count, pinned, deleted, edited_at. `link_preview_json` (nullable, `0061`) is the link card `{url, title, description, site_name, thumbnail_url}` this household built for the post's first link when it was created; NULLed on soft delete; its `thumbnail_url` (local `api/media/…`) counts as a live media reference. |
| `post_comments` | Threaded household post comments with `parent_id` self-reference. |
| `saved_posts` / `feed_read_positions` | Per-user saved posts and last-read marker. |
| `post_drafts` | Auto-saved post composer drafts. `context` is `household_feed`, a `space_id`, a `page_id`, or a `conv_id`. GC'd by `post_draft_scheduler`. |
| `polls` / `poll_options` / `poll_votes` | Household-feed polls. `polls` is keyed by the parent `feed_posts.id`. Votes are stored per `(option_id, voter_user_id)`. |
| `schedule_slots` / `schedule_responses` / `schedule_poll_meta` | Household-feed Doodle-style schedule polls. |
| `bazaar_listings` / `bazaar_bids` / `bazaar_offers` | Household-feed marketplace: fixed-price, offer, bid-from, negotiable, and auction modes. Bids vs offers are distinct concepts. |
| `saved_bazaar_listings` | Per-user saved listings. |
| `shopping_list_items` | Single shared household shopping list (§23.120). Each item optionally carries a free-form `store` name (auto-upserts a `shopping_stores` row on first sighting) so the SPA can render the list grouped by shop in trip order. |
| `shopping_stores` | Household's store catalogue + drag-defined "trip order". One row per `name` (PK), with `sort_order` driving the section order in the grouped shopping view. Auto-populated from `shopping_list_items.store`, or directly via `POST /api/shopping/stores`; rows are NOT removed when their last referencing item is deleted so the household keeps its order across empty lists. Names are unique **case-insensitively** — `ux_shopping_stores_name_nocase` (migration `0048`) — because the SPA's grouped view matches items against catalogue rows with an exact compare, so a `Migros`/`migros` fork renders the diverging items in *no* section at all. Every store-scoped repo operation (`_find_store`, `rename_store`, `delete_store`) resolves `COLLATE NOCASE` to match. |
| `household_theme` | Single-row (`id='default'`) household theme settings — primary/accent colour, surface, mode (`light`/`dark`/`auto`), font, density, corner radius. |
| `stickies` | Household + space sticky notes. `space_id IS NULL` means household-level. |

## Spaces

| Table | Purpose |
|---|---|
| `spaces` | Core space row — id (derived from space identity public key), name, owner, `space_type` (`private`/`household`/`public`/`global`), `join_mode` (the **membership** gate only — how a newcomer becomes a member who can post), `allow_subscribers` (the separate **readability** opt-in, default `0`/OFF, `0051_space_allow_subscribers.sql` — whether strangers may follow a public/global space read-only; with it off nothing is relayed to a connection server, no content key is sealed to a follower, and both `POST /api/spaces/{id}/subscribe` and `POST /gfs/subscribe` refuse. Independent of `join_mode`: `invite_only` + ON is a broadcast space, `open` + OFF is joinable but unreadable. Federates over `space_meta.features`), retention (`retention_days` + `retention_exempt_json`; mirrored to member households over `space_meta`, enforced only by the host), feature toggles (per-tab: calendar/todo/location/stickies/pages/gallery/bazaar), the per-post-type allow-list (`allow_post_*` — which post kinds members may compose in the feed; federates over `space_meta.features.allowed_post_types`), posts/pages/stickies/calendar/tasks access modes, `delegated_admin_authority` (owner opt-in, default `0`/OFF — authorises the space's admins to act on the owner's behalf while offline; the seed-share behaviour it gates ships later, `0030_space_delegated_admin_authority.sql`; federates over `space_meta.features`), public-discovery fields (lat/lon/radius), cover hash, `bot_enabled`, `min_age`, `category` (§23.50 discovery taxonomy — replaces the legacy `target_audience` age-band hint; `NULL` = unset → "general"; federates over `space_meta.category`, `0038`/`0039`), `dissolved`, `archived` (soft, reversible read-only archive — distinct from `dissolved` which is hard-gone; federates over `space_meta`), `archived_reason` (`NULL` for not-archived or a normal admin archive; `'dissolved'`/`'removed'` mark a remote-terminated archive — read-only, content kept, not unarchivable — pairs with `archived`), `welcome_version`, `tz` (the space's IANA wall-clock anchor for calendar events; defaults to the household tz at create time, editable by space admins for federated multi-household spaces that pin to a different city), `identity_private_key` (the KEK-wrapped Ed25519 space-authority seed matching `identity_public_key`; `NULL` for pre-upgrade or non-owned spaces — never federates, `0029_space_identity_private_key.sql`), and `config_author_instance` (the instance id that authored the last APPLIED config edit — the `(config_sequence, config_author_instance)` last-writer-wins tie-break key for v_24 admin-authoritative offline config edits; `NULL` for single-writer owner spaces, `0032_space_config_author.sql`), and `roster_sequence` (a dedicated monotonic counter for roster gossip — member join / role change / ban tombstone — decoupled from `config_sequence` so a role/ban no longer advances the config-LWW version and a delegated admin's offline config edit can't collide with the owner at an equal sequence; backfilled from `config_sequence`, `0036_space_roster_sequence.sql`), and `config_hlc` (a Hybrid Logical Clock `"<physical_ms>-<counter>"` advanced once per local config edit; the config-LWW tie-break key becomes `(config_sequence, config_hlc, config_author_instance)` so a genuinely-concurrent same-sequence edit resolves to the LATER one — intuitive, monotonic per node, drift-bounded across nodes — and a legacy `"0-0"` row / older sender ties under the HLC and falls back to the author tie-break, behaviour-identical to pre-0037; `0037_space_config_hlc.sql`), and `host_identity_pk` (the Ed25519 identity **public** key of the household hosting a remote space, hex — populated only on a *stub* whose host we are not paired with, from the sealed `SPACE_PRIVATE_INVITE` payload and only when `derive_instance_id(pk)` matches the envelope's authenticated sender. It is the sole key a **mesh-joined** member can verify the host's per-chunk `SPACE_SYNC_CHUNK` signatures with, since such a member has no `remote_instances` row for the host at all; deliberately space-scoped rather than seated in `remote_instances`, whose mere presence is what the §24.11 inbound pipeline gates on. `NULL` for owned spaces and for directly-paired hosts, `0045_space_host_identity_pk.sql`), and `authority_key_epoch` (`0066_space_authority_key_epoch.sql`, `INTEGER NOT NULL DEFAULT 0` — the rotation counter of `identity_public_key`: 0 is the creation-time key, each owner-certified rotation after an admin revocation bumps it (federation v_44). Written only by the owner's `rotate_authority_key` and a receiver's `adopt_authority_key`, both compare-and-set on it, never by the `save` upsert; a receiver re-pins only from a cert with a HIGHER epoch, so a replayed older cert can never restore a revoked key; the owner issues `max(current + 1, unix seconds)` so it stays ahead after a backup restore), `authority_baseline_epoch` (the epoch whose rotation-bundle baseline reset this household already ran — compare-and-set, so it runs once per epoch; a NEGATIVE value `-E` means "owed": the pin moved past rotated key epoch `E` without its bundle being claimed — written by `adopt_authority_key` in the same statement, so no column was added — and the next claim overwrites it; an owed epoch, or a post-restore bundle's `prior_key_epoch` above the claimed epoch, makes the post-restore bundle reset to the owner's snapshot), `authority_config_epoch` (the pin epoch under which the current config was applied; the baseline reset leaves a config applied under the new key alone), `authority_seed_shared_epoch` (owner side: the key epoch at which the signing seed was last shared with an admin household, `NULL` = never — a revocation with delegation already off still rotates when a seed for the current key is out; 0066 backfills `0` for every hosted space that holds its seed, since a pre-v44 owner never recorded its shares), `authority_cert_json` (`0068_space_authority_echo.sql`, nullable — the owner-signed cert for the key the row pins, as received by a member or signed by the owner; stored only while it matches the pin, one conditional UPDATE; it is the proof a member's authority epoch echo shows the owner, federation v_46), `authority_echo_json` (`0068`, nullable JSON — this household's echo state: on a member `{forgotten_epoch, forgotten_cert}`, a rotation the restored owner forgot, kept until a bundle names it so a restart does not lose it; on the owner the header of its last rotation `{epoch, baseline, prior_key_epoch, forgotten_key_epoch, max_forgotten, max_baseline, restore_prior, restore_epoch}` — the last two the window the post-restore rotation recorded, the only epochs a member can prove were forgotten, so a re-sent bundle says what the original said), and on a follower mirror `mirror_gfs_id` (the GFS connection that seated it) + `gfs_rotation_seq` (that GFS's last `authority_rotation_seq`) — a follower re-pins from that GFS only, to a higher seq. On a stub, `owner_user_id` (`0070_space_owner_user_id.sql`, nullable) names the owner's seat — the owner is mirrored as a plain `space_remote_members` row (no remote `owner` shape), so this is how the stub refuses (and stops offering) a role change on it; taken from the host's own `role: "owner"` entry in the invite / redeem-ACK roster and in the host's own `SPACE_ROSTER_SNAPSHOT` (trusted only when the host sent it), written only by `set_owner_user_id`, and cleared by `record_owner_change` when the host's config reports a new `owner_username` after an ownership transfer; `NULL` on hosted spaces (`users` answers there) and on stubs seated before 0067. |

| `global_spaces` | One row per public/global space published to this GFS — `owning_instance`, branding (name, description, about, cover/icon data URIs, colours), `status`, subscriber/posts bookkeeping, and `category` (the §23.50 discovery taxonomy, signed in the owner's `publish_space` body; GFS migration `0007` added it and dropped the legacy `target_audience`). `identity_public_key` (the space's Ed25519 *authority* verify key, hex) is **TOFU-pinned on first publish** (GFS migration `0004`); the `upsert_space` conflict clause never moves a set pin (`COALESCE(NULLIF(global_spaces.identity_public_key,''), NULLIF(excluded.identity_public_key,''))`) so no ordinary write — publish refresh or cluster `NODE_SYNC_SPACE` — can clear or replace it. Withdrawn rows are excluded from the discovery reads (`list_spaces`, the detail route, the public pages) but still returned by `get_space`, which `publish_space` needs for its owner-immutability and TOFU-pin checks, and by `list_spaces(include_withdrawn=True)`, the moderator read behind the admin console — withdrawal hides a space from discovery, never from moderation. The owner's next signed publish clears the flag. `join_mode` (GFS migration `0009`, default `'invite_only'`) is the owner's **membership** gate, signed in the publish body (`invite_only` / `open` / `request`) and normalised on both write and read — an unknown value fails closed to `invite_only`; it is shown on the directory listing and says nothing about readability. `allow_subscribers` (GFS migration `0010`, default `0`) is the owner's **readability** opt-in, likewise signed in the publish body. A space with `allow_subscribers = 0` is listed for DISCOVERY but is **not publicly readable**: `POST /gfs/subscribe` refuses it with a 403, and a publish carrying an **explicit** `allow_subscribers: false` purges the space's `space_subscribers` rows (logged at INFO with the count) so a seat taken while the space was readable cannot linger — a publish that merely OMITS the key (an older household) gates without purging, and households re-register their seats on each GFS-WS reconnect (`GfsSpaceMirrorService.resubscribe_all`). Both defaults are deliberately fail-closed rather than backfilled: every pre-migration row reads as invite-only and unreadable until its owner's next GFS-WS connect re-publishes the metadata (`GfsConnectionService.heal_space_pins`), which is one reconnect away. Both travel on cluster gossip alongside `withdrawn` so a peer sync cannot silently re-close a readable space or mislabel its way in. `content_epoch_confirmed`, `content_epoch_prev`, `content_epoch_seen_at`, `content_epoch`, `content_epoch_raised_at` (GFS migration `0014`, all nullable INTEGER, v_49) hold what `POST /gfs/member-publish` checks a writer cert's epoch against, in two tiers: the epoch the space OWNER last confirmed (owner-household-signed notice), the confirmed one before it, and when (unix seconds) — moved only by the owner, up to `max(confirmed + 1000, now + 1 day)`, the first confirmation storing `epoch − 1` as predecessor; and `content_epoch`, the newest epoch seen at all, which seed-only statements (a delegated admin's notice, an authorized `space_post_public` relay) raise by exactly +1 at most once a minute (`content_epoch_raised_at`) and never below the confirmed tier. Writer certs write none of them. Each write is one conditional statement, never `upsert_space`; all five are cleared by `set_space_authority` when the authority key is re-pinned, and none is on the `GlobalSpace` dataclass, so the public directory never serves them. `NULL` confirmed = no owner confirmation yet. |

| `gfs_envelope_queue` | Store-and-forward queue for sealed household-to-household envelopes relayed by `POST /gfs/envelope` (GFS migration `0011`, §D2b invite bootstrap). Indexed on `(to_instance, created_at)`: the drain reads one recipient's rows in insertion order on its next authenticated hello and deletes each only after its frame went out. Retention is enforced in code, not by trigger — `ENVELOPE_QUEUE_TTL_SECONDS` (24 h, so an invite link doesn't fail because the issuing household is asleep) swept hourly by the GFS maintenance loop, and a two-sided per-recipient ceiling enforced inside the insert transaction — `ENVELOPE_QUEUE_MAX_PER_RECIPIENT` (2000 rows) and `ENVELOPE_QUEUE_MAX_BYTES_PER_RECIPIENT` (64 MiB), whichever is reached first — bounding what an anonymous flood aimed at one household can store. At either ceiling the **new** envelope is dropped (**tail-drop**), never the oldest: the endpoint is unauthenticated, so evict-oldest would hand any stranger who knows an instance id a delete primitive over a sleeping household's queued mail. The drop is logged at WARNING with the recipient and the current depth, and still answered with the same uniform `202`. The two kinds are capped separately, so a busy space can never crowd out a household's envelopes: relay items per recipient (250 rows / 4 MiB, `RELAY_QUEUE_MAX_*`; the recipient's own oldest item makes room) and server-wide (`RELAY_QUEUE_MAX_TOTAL_BYTES`, 256 MiB, summed from `size_bytes` (GFS migration `0014`, `INTEGER NOT NULL DEFAULT 0`, the row's `LENGTH(sealed_json)` written on insert) through the covering index `idx_gfs_envelope_queue_relay_size (frame_type, to_instance, expires_at, size_bytes)`, so no cap check ever reads a stored blob; the largest holder's oldest item makes room), all inside the insert's transaction (`enqueue_relay`). Relay rows are written only for subscribers whose `client_instances.relay_seen_at` (GFS migration `0014`, nullable INTEGER — set once a `/gfs/ws` session has stayed open 60 s; a bare hello never sets it) is within the 24 h TTL. |
| `gfs_pair_tokens` | Single-use public-pairing tokens (§24.7.4) with a 10-min TTL. Counted within a short rate-limit window, then dead weight; pruned after 24 h (`PAIR_TOKEN_RETENTION_SECONDS`) by the GFS maintenance loop. |
| `gfs_invite_tokens` | Owner-minted space invite links (§24.8.5) — the connection server's bulletin board.

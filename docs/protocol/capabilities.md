# Capabilities — federation protocol version

## Why this exists

Peers run different builds. Adding a new federation surface (a new
event type, a new payload field whose default-if-missing would be
*wrong* rather than just "unknown") means the sender has to know
whether the receiver understands it. Two failure modes if it doesn't:

* **Unknown event type** — the inbound event registry returns "no
  handler" and the event is dropped at the boundary. Source and target
  end up with diverging state (e.g. one calendar shows Dec 23, the
  other still shows Dec 24).
* **Missing-default bug** — the receiver does `.get("new_field",
  default)` but the default is wrong for the new semantics (e.g. a new
  `event.privacy` field whose default would silently make everything
  public).

A single monotonic integer on each peer fixes both: the sender checks
the integer before sending and either picks a degraded shape or skips
that peer.

## On the wire

Every `remote_instances` row carries `proto_version: int`. The local
build declares its current version in
[`socialhome.domain.federation_capabilities.OURS`](../../socialhome/domain/federation_capabilities.py).
At startup the
[`CapabilitiesOutbound`](../../socialhome/services/capabilities_outbound.py)
service fans out a single envelope to every confirmed peer:

```
FederationEventType.INSTANCE_CAPABILITIES_UPDATED
payload = {"proto_version": <our int>, "display_name": <our household name>}
```

The receiver's [pairing inbound
handlers](../../socialhome/services/federation_inbound/pairing.py)
upsert the value onto the sender's `remote_instances` row. Peers that
haven't sent the announcement yet read as `proto_version=1` — the
oldest known wire — so any gate above v1 returns `False` until the
first envelope lands.

The optional **`display_name`** field carries the sender's federated
household name (`instance_identity.display_name`). The receiver writes it
onto the peer's stored *advertised* `remote_instances.display_name` (via
`update_display_name`) so a rename reaches **already-paired** peers, not
just QR-time pairings — fixing the case where both households still showed
the QR-time name after one renamed itself. Two notes on the inbound side:

* The name is applied **before** the `proto_version` short-circuit, so a
  rename re-broadcast (same `proto_version`, new name) still lands.
* It touches only the *advertised* `display_name`, never a local
  `local_alias` — an admin-set alias keeps winning in
  `RemoteInstance.effective_display_name`.

The field is **additive + fail-soft** and needs no version bump: older
senders omit it, and a receiver that gets a missing / blank `display_name`
keeps the prior name. No `proto_version` gate is required because dropping
the field is benign (the name just doesn't refresh).

## Sender-side gating

Outbound code consults
`FederationService.peer_supports(instance_id, min_version=N)` before
including optional v_N fields:

```python
payload = {"start": event.start, "end": event.end, ...}
if await self._federation.peer_supports(peer_id, min_version=2):
    payload["tz"] = event.tz
```

The convention is "send-the-old-shape-when-unknown" — `peer_supports`
returns `False` for any peer we don't have in `remote_instances` or
that hasn't announced yet, so the legacy shape always reaches the
peer; new fields are added only when we positively know the receiver
will parse them.

## Bumping the version

When a release adds a federation surface whose default-if-missing
would be wrong (or a brand-new event type old peers can't dispatch):

1. **Bump `OURS`** in
   [`socialhome/domain/federation_capabilities.py`](../../socialhome/domain/federation_capabilities.py)
   to the next integer.
2. **Add a named constant** to `FederationCapability` so call sites
   reference the version by intent
   (`FederationCapability.MIN_FOR_OCCURRENCE_OVERRIDE`) instead of a
   magic number. Document what changed in v_N in the history list at
   the top of that module.
3. **Pick a §319-paragraph-5 policy** for the new feature: `skip` /
   `fallback` / `force-upgrade`. Record it in the **Policy** column
   of the version history below so future contributors know what
   degraded shape (if any) old peers should receive.
4. **Wire the transform** when the policy is `fallback`: add a
   one-file shim under
   [`socialhome/federation/compat/`](../../socialhome/federation/compat/)
   that registers a per-event transform. The main service code calls
   `compat.transform_for_peer(...)` once per outbound — the rewrite
   lives entirely in the compat tree, never sprinkled across
   services. Dropping support for v_N later is then a single-file
   delete here.
5. **Update this page** with a one-line summary of v_N: what changed,
   what the older-peer fallback is.
6. **Add a test** that asserts `peer_supports` returns `False` for the
   old shape and `True` for the new one (and that the compat shim
   produces the documented fallback for a sub-v_N peer).

| **24** | **Admin-authoritative offline config edits** (owner-offline-spaces epic Phase 4a). `SPACE_CONFIG_CHANGED` is now **space-authority-signed**: the emitter (owner host OR a seed-holding delegated admin) signs the config `space_meta` with the space's Ed25519 seed (`sign_authority_event`), and the receiver (`_on_space_config_changed`) accepts the edit by verifying `authority_sig` / `authority_sig_suite` against `spaces.identity_public_key` rather than requiring `from_instance == owner_instance_id`. This lets a delegated admin change a space's config (name / description / emoji / features / join-mode / retention / about) while the owner is offline; every member household — including the offline owner on reconnect — accepts it. An emitter holding the seed for a `delegated_admin_authority`-ON space executes the edit LOCALLY + authoritatively in `update_config` (bumps `config_sequence`, persists, broadcasts the signed event) instead of forwarding the v_15 `SPACE_REMOTE_ADMIN_ACTION` to the host; without the flag or the seed it keeps the v_15 forward-to-host behaviour. The signed `space_meta` carries `config_author_instance` (the editing household). Concurrent same-`config_sequence` edits from two admins converge via a deterministic `(config_sequence, config_author_instance)` lexicographic last-writer-wins tie-break recorded on the receiver in `spaces.config_author_instance` (migration 0032): apply iff `(incoming_seq, incoming_author) > (existing_seq, stored_author)`, equal → no-op. **Security, fail-closed:** a PRESENT authority signature MUST verify — a present-but-invalid / unknown-suite / wrong-key signature DROPS the event (it never falls through to the owner gate); a non-owner with NO signature is dropped (today's behaviour). Toggling `delegated_admin_authority` itself stays OWNER-only (unchanged). Gated on `FederationCapability.MIN_FOR_ADMIN_AUTHORITATIVE_OPS` (space-scoped). | **best-effort, gated** | The owner / seed-holder gates the signed broadcast on `peer_supports(min_version=24)`; a sub-v_24 member household has no authority-verify path, so it falls back to the legacy owner-only gate (a delegated admin's offline edit is dropped there until the owner re-broadcasts / §25.6 sync reconciles). An owner-originated edit still applies on a sub-v_24 peer via the legacy `from_instance == owner` path (back-compat). The per-space compatibility banner warns when a member household lags. |
| **22** | **Delegated-admin signing-seed share** (`SPACE_ADMIN_KEY_SHARE`, delegated-admin epic Phase 1). When the space owner opts into `SpaceFeatures.delegated_admin_authority`, the owner ships the space's Ed25519 signing seed (the private half of `identity_public_key`) to a REMOTE admin household so that household can sign space-authority events with the owner offline. Triggered on two owner-side edges: promoting a remote member to ADMIN (`set_remote_member_role`) and flipping the flag False→True (`update_config` distributes to every current remote admin household via `space_remote_members.role == 'admin'`, deduped by instance). The seed travels ONLY over the encrypted peer-pair path (`send_with_mesh_fallback` → the directional session key), addressed to that one household — **never broadcast**. Payload: `{space_id, space_seed: b64url(32-byte seed), seed_suite: "ed25519-seed"}`; the suite tag is validated against `SUPPORTED_SEED_SUITES` with no default fallback. The receiver **fails closed** — it stores the seed only when the §24.11-verified `from_instance` is the space's `owner_instance_id` AND its own local copy of the space has `delegated_admin_authority` ON AND the seed b64url-decodes to exactly 32 bytes under a known suite; any other shape is dropped (logged) and nothing is stored. Receipt is logged at INFO (key-blast-radius audit). Turning the flag back off does NOT revoke already-shared seeds (deeper revocation — seed rotation — is a later phase). Gated on `FederationCapability.MIN_FOR_SPACE_ADMIN_KEY_SHARE` (space-scoped). | **fail-closed, no fallback** | The owner gates the send on `peer_supports(min_version=22)`; a sub-v_22 admin household has no handler, so the owner SKIPS the send and logs at WARNING (that admin simply can't act on space authority offline until it upgrades) rather than shipping a private signing key at a peer that would drop it. There is no safe degraded way to distribute a private key, so the gate is hard. The per-space compatibility banner warns when an admin household lags. |
| **25** | **Per-user identity binding** (per-user identity Phase 1). `USERS_SYNC` / `USER_UPDATED` payloads may now carry a per-user identity binding — the user's public key plus a dual-signed assertion binding that key to the user on this household — so a receiver can attribute federated user activity to a stable per-user identity rather than the household-scoped `user_id` alone. The extra field is gated on `FederationCapability.MIN_FOR_USER_IDENTITY_KEY`; the legacy `user_id` field is unchanged and unaffected. Per-user surface, not space-scoped — its lag affects only the two households exchanging the user roster, so it is intentionally excluded from the per-space compatibility banner. | **best-effort** | A sub-v_25 peer receives the legacy user shape (no per-user identity key) and keeps addressing users by `user_id` exactly as before. The sender gates the identity-binding field on `peer_supports(min_version=25)`, so older peers keep working with no user-visible regression — only the per-user identity attribution is unavailable until both sides upgrade. |
| **26** | **UUID identity anchor** (per-user identity Phase 2). `USERS_SYNC` / `USER_UPDATED` payloads may now carry an `identity_anchor` field — an immutable identifier (UUID for newly-created users, frozen username for existing users) that anchors the `user_id` derivation instead of the current username. This ensures a user's `user_id` remains stable across a rename, so federated identity attestations and activity history don't fragment when a household renames a local account. The extra field is gated on `FederationCapability.MIN_FOR_IDENTITY_ANCHOR`; the legacy `user_id` field (derived from username) is unchanged and unaffected. Per-user surface, not space-scoped — its lag affects only the two households exchanging the user roster, so it is intentionally excluded from the per-space compatibility banner. | **best-effort** | A sub-v_26 peer receives the legacy user shape (no identity_anchor) and derives `user_id` from the current username exactly as before. The sender gates the identity_anchor field on `peer_supports(min_version=26)`, so older peers keep working with no user-visible regression — only the stable identity anchor is unavailable until both sides upgrade. The public/global-space post relay (GFS path, **no** proto negotiation) also signs the anchor inside the per-author inner — there `build_signed_author_inner` normalises a legacy username-anchored author (`identity_anchor == username`, the `0041` backfill) to *no anchor key*, so their signed bytes stay byte-identical to v_25 and verify on any subscriber; only uuid4-anchored (v_26+ provisioned) authors carry it and verify on v_26+ only. See [`discovery.md`](./discovery.md). |
| **27** | **Move-out link** (MO-1). Two new event types — `USER_MOVED` (the *old* home pushes a dual-consent `MoveLink`) and `USER_IDENTITY_RESOLVE` (a pull backstop a confirmed peer uses to fetch the stored link it missed) — redirect a moved person's `old_user_id@old_home` → `new_user_id@new_home`. The `user_id` stays **household-scoped** (provenance, never re-keyed); the portable identity is the per-user pubkey `P` (v_25 binding). Accepting requires **dual consent** (a user signature by `P` + a destination-pinned old-home release signature by the old home's instance key) plus both `P`-bindings verifying; replay is defended by a **monotonic `issued_at`** keyed on `P`. Distribution is push (`USER_MOVED` to v_27+ confirmed peers) + confirmed-peers-only pull (`USER_IDENTITY_RESOLVE`). Gated on `FederationCapability.MIN_FOR_USER_MOVE`. Per-user surface, not space-scoped — its lag affects only the households tracking the moved user, so it is intentionally excluded from the per-space compatibility banner. See [`move-out.md`](./move-out.md). | **best-effort** | A sub-v_27 peer is not pushed to and cannot resolve, so it keeps the **stale contact** pointing at `old_user_id@old_home` — **no data loss and no auto-follow** (old content stays attributed to the old `user_id`; the peer never silently re-points). Once it upgrades, the pull backstop / next push re-points it. |
| **28** | **Mesh route-stale nack.** New event type `SPACE_ROUTE_STALE`. A `SPACE_ROUTED` target whose cached ephemeral X25519 private half is gone (it restarted — the key lives only in RAM) no longer drops the envelope in silence: it signs `b"space-route-stale:v1:" + route_id + b":" + stale_eph_pk` with its Ed25519 identity key (`sig_suite` tagged, `ed25519` today) and sends the nack back along the reverse path. The origin verifies the signature against the target identity pub it pinned at discovery, invalidates the cached route, and retransmits once via fresh `SPACE_FIND_ROUTE`. Domain-separated from `space-route-found:v1:` so a captured ROUTE_FOUND signature can't tear down a live route. Gated on `FederationCapability.MIN_FOR_ROUTE_STALE_NACK` (space-scoped). | **best-effort** | A sub-v_28 hop drops the nack, so the origin keeps sealing under the dead key until `route_discovery.ROUTE_CACHE_TTL_S` expires and rediscovers — exactly today's behaviour (the #648 window). No data loss; the nack only shortens the outage. The per-space compatibility banner warns when a member household lags. |

## Future extensions

A *per-peer feature flag set* (a string-named set on top of the
integer) is deliberately deferred. The flag layer earns its complexity
once we have selective deployments (admin turns off a feature),
asymmetric send/receive support, or third-party forks — none of which
exist today. Adding `features TEXT NOT NULL DEFAULT '[]'` to
`remote_instances` is a one-line additive migration when real
operational evidence forces it.

`INSTANCE_RESYNC_REQUEST` shipped in v_19 (see the history table above).
One related idea still fits the same announcement channel:

* An admin-UI panel that diffs `peer.proto_version` against `OURS` per
  peer and surfaces "this peer is behind, [X] features won't work with
  them yet" hints. Pure UI on top of the existing column — no new
  wire shape. **Shipped:** the household-wide admin panel
  (`GET /api/admin/federation/compat`) plus a per-space banner
  (`GET /api/spaces/{id}/compat`, #319 ¶5) that diffs each member
  household and warns which shared-space features lag; the per-space
  subset is driven by `space_features_missing_below` over
  `SPACE_SCOPED_MIN_VERSIONS`. Both skip member households that have
  never advertised capabilities so a mid-handshake peer isn't flagged.
